01 / PURPOSE · 10 MIN

Text is content. A path is authority.

In Lesson 02, the request supplied the text itself. With media, a request can point at a file. If the tool blindly opens whatever path it receives, it can turn a harmless “attach a chart” instruction into access to unrelated documents. That is a different risk, even before Telegram sees a byte.

Imagine a dedicated tray marked outgoing. The caller may name an item in that tray, not rummage through the whole building. A configured root alias is the tray's name. A relative path names an item inside it. Trusted server code must still establish that the item really belongs there.

Build understanding, not another connector. The current connector already implements text and media sending. This lesson builds a deliberately smaller, offline policy, then compares it with the real implementation. Do not enable sending, change permissions, create upload roots, or use personal files for this exercise.

Carry forward

Validation before action. Typed outcomes. Tests for rejected requests. Honest uncertainty after dispatch.

Add one new boundary

Turn an untrusted file request plus trusted observations into a bounded Ready value. There is no sender in today's model.

Pace: purpose 10m + theory 25m + simulator 15m + Rust practice 35m + source reading 15m + recap 10m = 110m. If you have one hour today, stop after the simulator and resume at Rust practice. Optional extension: 20m.

02 / THEORY BEFORE CODE · 25 MIN

Claims enter. Evidence leaves.

1. An alias limits the place, not just the spelling.

A request such as {root: "outgoing", relative_path: "images/chart.png"} refers to a directory configured on the connector's host. It is not a path on whichever laptop is running the chat app. Using an alias avoids letting every request choose an arbitrary absolute root. The server, not the model, owns that mapping.

First reject clearly invalid syntax: an empty path, an absolute path, or a .. component. But syntax alone is not containment. A symlink inside the directory can refer outside it. A hard link can give another name to an existing file. A directory or device is not a regular attachment. Even a prefix test can be wrong: /safe-old starts with the text /safe, but is not inside that directory.

Do not turn this toy into a security library. Our path grammar intentionally accepts only nonempty slash-separated components, with no dot components, backslashes, colons or NUL. It is a portable teaching subset, not a reproduction of the connector's full path contract. It cannot inspect symlinks, permissions or file identity.

2. Check the bytes you will actually use.

A filename ending in .png is a claim. A bounded header inspection can provide evidence about a format. Even a plausible signature is not proof that the entire image decodes safely, is benign, or will be accepted by Telegram. A type check and a malware scanner are not the same thing.

Likewise, a size supplied in a request is untrusted. The host must observe a file's size and enforce a cap while preparing it. “The file was small when I checked” is not enough if it grows during copying. Here, 10 MiB = 10 × 1024 × 1024 = 10,485,760 bytes. The maximum is inclusive; zero bytes is rejected.

3. Validation and use must refer to the same thing.

Suppose you check file A, then a program replaces the path, then you open it again. You might upload file B. This is a time-of-check/time-of-use problem: the world changed between your check and your action. A private snapshot, identity checks and controlled readers help bind preparation to later upload. A naive “canonicalize, then open the path later” sequence still leaves room for change.

The real connector takes a verified private snapshot and uploads that snapshot. Our model does not open or copy anything. A supplied Observation stands in for evidence gathered by a trusted adapter. In a real system, you cannot let the caller set safe_regular = true and treat that as proof.

4. A new state is not a stronger receipt.

Ready means our local teaching checks passed. It is not a Telegram receipt. An upload can succeed while the final message fails; consequently the connector's not_sent does not guarantee that no attachment bytes reached Telegram. Lesson 02's final delivery states still matter after local preparation.

Request: untrusted claims

Root alias, relative path, requested kind and caption. They describe intent, not proof.

Observation: trusted adapter output

Observed size, inspected kind, regular-file boundary and stable snapshot evidence. In this lab they are synthetic.

Why bound memory and disk separately?

A file-size cap limits one item. A concurrency limit bounds how many preparations can run at once. A staging quota limits retained private copies. Streaming avoids loading the entire attachment into memory, but does not erase disk use, upload buffers or cleanup work. We defer implementing those mechanisms; recognize the separate budgets when reading the real code.

04 / OFFLINE RUST · 35 MIN

Keep policy small enough to see.

Download the starter into a disposable scratch folder, not into the connector. It includes the request and observation types, ten tests and one todo!. Implement only preflight. No external crates, async runtime, files or network are needed.

rustc --edition=2021 --test lesson-03-starter.rs -o lesson03-tests
./lesson03-tests

The initial tests should fail at todo!. Work from the first failure, then rerun all tests. The reference is for comparison after your attempt, not a replacement for it. You need an installed Rust toolchain to run these commands.

  1. Require the root alias outgoing.
  2. Apply the narrow path grammar described above. Reject empty components too: a//b.png is deliberately outside this toy grammar.
  3. Reject captions above 1,024 UTF-16 units. An empty caption is allowed.
  4. Reject unless the synthetic file evidence says regular/safe and stable.
  5. Require size in 1..=10 * 1024 * 1024.
  6. Require requested kind to equal inspected kind. Return Ready with observed size and kind.

Return the first error in that order. This makes multi-error cases predictable and keeps the browser and Rust versions aligned. Result<Ready, &'static str> is convenient for this small exercise; production APIs typically use richer typed errors.

Hint: why this type shape?

A Request describes what was requested. An Observation describes what was found. A Ready is only constructed on the successful branch. Separating these types prevents your function from quietly treating claims as evidence. In this standalone example tests can construct observations directly; a real adapter would control that construction.

if observation.size == 0 || observation.size > cap {
    return Err("size");
}
// Only after all checks:
Ok(Ready { size: observation.size, kind: observation.detected })
Reference implementation

What the tests establish: deployment checks exercise the Rust reference and the browser model separately. Passing tests validate this in-memory policy, not filesystem security or Telegram behavior.

Three differences to write down: the real connector obtains filesystem evidence rather than trusting booleans; stages a private snapshot with bounded resources; and later uploads/sends with receipts and uncertain outcomes. Our policy does none of those operations.

06 / RECALL WITHOUT LOOKING · 10 MIN

Explain it to your future self.

  1. Why is a path different from text content?
  2. Why can a relative path still refer to an unsafe file?
  3. Why is a snapshot useful after validation?
  4. What do Ready, uploaded and Sent mean, and why are they different?
  5. What evidence would you need before trusting this toy with real files?
Compare your explanation

A path asks a host to exercise filesystem authority. An alias and syntax rules reduce what can be requested, but links, identity, permissions and races need trusted filesystem controls. A verified private snapshot ties the inspected bytes to subsequent use. Ready only means local checks passed; uploaded means bytes were transferred; Sent needs a matched acknowledgement for a message. The toy has no secure adapter, no real snapshot, no resource admission, no uploader and no delivery evidence.
