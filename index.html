01 / THE MENTAL MODEL20 minutes

One connector. Two conversations.

AI-facing boundary

MCP

The AI application discovers and calls tools exposed by your connector. rmcp handles this side of the protocol.

Telegram-facing boundary

Telegram API / MTProto

The connector uses grammers to communicate with Telegram. This is separate from the Bot API used by a dedicated bot identity.

Follow the request

A conceptual flow, not a network trace. Step through it to see which component is responsible.

AI appChooses a tool
MCP toolReceives inputs
ValidationChecks policy
ClientCalls Telegram
TelegramReturns a result
1 / 5 · The AI application requests an operation. A model's request is not permission to send to any recipient.

Key idea: an MCP request is not itself a Telegram message. Your application validates the inputs and decides whether to invoke the Telegram client.

Read: MCP architecture overview ↗Focus only on Participants, Layers and Primitives.Read: Telegram APIs ↗Read the introductory Bot API / Telegram API sections. Skip cryptography and method catalogs.
Self-check: why doesn't adding an MCP tool automatically enable sending?

It exposes an interface to the AI application. The connector still needs validation, a sending implementation and the appropriate Telegram account permissions. An interface declaration alone does not perform the operation.

02 / READ THE EXISTING CODE20–25 minutes

Trace one call, not the whole project.

Find get_channel_info_data and follow it into the replaceable Telegram client boundary. These links point to the public repository's current master; paths may evolve.

  1. src/mcp/server.rs
    Locate the MCP server and its entry points.
  2. src/mcp/server/impl_channels.rs
    Follow input validation, rate-limit token acquisition and the client call.
  3. src/telegram/trait_def.rs
    Find TelegramClientTrait::get_channel_info. Read its retry policy.

Your task: sketch the route in three lines. Mark where input validation happens and where a real client could reach the network. Notice that a trait call can also be fulfilled by a fake client.

03 / A SAFE EXPERIMENT15–20 minutes

Replace the outside world.

Read examples/inert_server.rs and its OfflineClient. The example constructs a server and checks its status without authenticating or loading a real Telegram session.

In your existing local checkout, with the pinned toolchain and dependencies already available:

cargo run --offline --locked --example inert_server

A successful run may finish silently if its assertions pass. --offline tells Cargo not to fetch dependencies; the example's offline client is what avoids Telegram access.

If dependencies are missing: stop at reading the example tonight. No account setup is needed. Never paste session files, tokens or credentials into your notes.

Why substitute the client?

A fake or offline client makes outcomes predictable. You can test input handling and failures without accidentally messaging somebody, needing credentials or depending on the network.

04 / DESIGN BEFORE IMPLEMENTATION30–45 minutes

The smallest safe send.

Write a short contract for a proposed operation: exactly one explicit destination and plain text only. No media, broadcasts, scheduling or real sending tonight.

Before dispatch

  • Reject empty text.
  • Reject missing or ambiguous destinations.
  • Allow only the intended test destination.
  • A preview must transmit nothing.

After dispatch

  • Return a message ID on confirmed success.
  • Distinguish a known failure from an unknown outcome.
  • Do not blindly retry an ambiguous timeout.

The important failure: Telegram might receive a message even if the reply to your connector gets lost. “I didn't receive confirmation” does not mean “nothing happened.” Retrying can send a duplicate.

Interactive thought experiment · no network calls

What should a fake sender do?

Choose a case to reveal the expected behavior. These are proposed tests, not tools already implemented in the repository.

Write these five tests in your own words. There is no need to add a method to TelegramClientTrait yet: it is a public compatibility surface, so the extension deserves a deliberate design.
