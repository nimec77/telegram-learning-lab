Lesson 7: Find the right evidence before drafting

Duration: 105 minutes | Rust | TeleShelf support assistant

In Lesson 6 you manually selected facts and checked a cited draft. This time you will build a tiny retrieval system that selects the facts itself. No model API, vector database, Telegram connection or real customer data is needed.

1. Theory (20 min)

RAG (retrieval-augmented generation) has two distinct stages:

  • Retrieval finds relevant evidence from a collection of documents.
  • Generation uses that evidence to produce an answer.

A document can be relevant to the words in a question and still be wrong for the user's installed version. Metadata (version, platform, source) is therefore as important as a relevance score. Keyword matching is a simple baseline; embeddings later let you compare meanings even when words differ. Read Google's embedding introduction (focus on the introductory explanation and word embeddings).

3. Implement retrieval (35 min)

Start with this baseline in src/lib.rs:

use std::collections::HashSet;

#[derive(Debug)]
pub struct Entry {
    pub id: &'static str,
    pub version: &'static str,
    pub keywords: &'static [&'static str],
    pub evidence: &'static str,
    pub source: &'static str,
}

#[derive(Debug, PartialEq, Eq)]
pub enum Decision<'a> {
    Evidence(&'a str),
    Clarify,
    HandOff,
}

pub fn score(q: &str, keywords: &[&str]) -> usize {
    let words = q.to_ascii_lowercase();
    let tokens: HashSet<_> = words
        .split(|c: char| !c.is_ascii_alphanumeric())
        .filter(|s| !s.is_empty())
        .collect();
    keywords.iter().filter(|k| tokens.contains(**k)).count()
}

pub fn retrieve<'a>(
    entries: &'a [Entry],
    question: &str,
    version: Option<&str>,
) -> Decision<'a> {
    let Some(version) = version else {
        return Decision::Clarify;
    };
    let mut candidates: Vec<_> = entries.iter()
        .filter(|e| e.version == version)
        .map(|e| (score(question, e.keywords), e))
        .filter(|(s, _)| *s >= 2)
        .collect();
    candidates.sort_by_key(|(s, _)| std::cmp::Reverse(*s));
    match candidates.as_slice() {
        [] => Decision::HandOff,
        [(s1, _), (s2, _), ..] if s1 == s2 => Decision::Clarify,
        [(_, best), ..] => Decision::Evidence(best.id),
    }
}

Populate the three entries yourself using the table. The threshold of two keyword matches is a teaching heuristic, not a probability of correctness. Only pass the selected evidence and source into the draft stage from Lesson 6. If the decision is Clarify, ask for the version or more details. If HandOff, tell the support owner no applicable evidence was found. Do not send anything automatically.

5. Connect retrieval to generation (10 min)

For a selected entry, create a prompt containing the fictional user question, installed version, only the chosen excerpt and its source. Ask the model (or simulate its result) to draft only what the source supports. Have your review stage reject a proposed answer claiming there is a new account-reset setting: the release never documents one, even if the citation is correct.

Done when: all eight retrieval cases pass, you can explain why the wrong version cannot win even with a perfect word match, and the draft stays review-only. The core idea is simple: retrieval quality is a separate engineering problem from generation quality.

Optional extension: experiment with a synonym list such as avatar → photo. Add a test before changing the algorithm. Next lesson we can compare keyword retrieval with embeddings, using this same small fixture.
