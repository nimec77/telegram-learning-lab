01 / START WITH THE PURPOSE · 10 MIN

Before adding intelligence, control actions.

An assistant may ask a tool to send a reply. The tool must still reject invalid requests, obey the application's permission policy, and report what actually happened. Otherwise a persuasive model can trigger a wrong recipient, a duplicate, or a false success message.

The project moved forward: Telegram Connector v0.26.0 already contains opt-in text and media sending. This lesson adapts to that reality: build a tiny teaching version separately, then compare it with the real code. Do not add a second implementation to the connector.

Lesson 01 designed the contract. Now implement its core without authentication, uploads, async code or MCP wiring. Those are important, but they would obscure today's three ideas.

What belongs here

Local validation, a fake sender, explicit outcomes and tests that count calls.

What waits

Real sending, media, support automation and AI-generated replies. No production configuration changes.

02 / THEORY BEFORE CODE · 30 MIN

A timeout is not a receipt.

Imagine posting a letter. If you still hold it, you know it was not posted. If the recipient confirms arrival, you know it arrived. If you posted it but heard nothing back, neither conclusion is justified.

Before dispatch

Validation: is the text usable and destination explicit?
Authorization: is this operation allowed?
Fail here and the sender must not be called.

After dispatch

A confirmed receipt gives Sent. A definitive refusal gives NotSent. A lost response after the request may have reached the service gives Unknown.

Why a fake sender?

A trait is a seam between policy and the outside world. A fake records how many times it was called and returns a scripted outcome. It proves the policy behavior without proving anything about Telegram delivery. Testing the real adapter is a later, separate task.

Why not retry until it works?

Retries are safe only when the operation's semantics make them safe. An ambiguous send may already have happened. A new attempt can create another message. The teaching model makes one call and propagates the outcome; it does not promise exactly-once delivery across repeated user requests.

Why count UTF-16 units?

The connector's text contract caps text at 4,096 UTF-16 units. Rust's str::len() counts bytes. chars().count() counts Unicode scalar values. Neither is the same. For example, "😀" is four UTF-8 bytes, one scalar value, and two UTF-16 units. Use encode_utf16().count(). Check blankness with trim(), but preserve the original text.

Before your implementation, all eight tests fail at todo!. That's intentional. Work through them in order:

  1. Reject disabled policy before dispatch.
  2. Reject destinations other than the literal fake test-room.
  3. Reject blank text and text over 4,096 UTF-16 units. Preserve valid text verbatim.
  4. Return Preview without calling the sender.
  5. Otherwise call the sender once and return its outcome unchanged.

// A teaching model only: no Telegram, credentials, files, or network.
#[derive(Debug, PartialEq)]
enum Outcome { Preview, Sent(u64), NotSent(&'static str), Unknown }
#[derive(Clone, Copy)]
enum Mode { Preview, Dispatch }
struct Request<'a> { destination: &'a str, text: &'a str }
trait Sender { fn send(&mut self, request: &Request<'_>) -> Outcome; }
fn execute(request: &Request<'_>, enabled: bool, mode: Mode, sender: &mut impl Sender) -> Outcome {
    if !enabled { return Outcome::NotSent("disabled"); }
    if request.destination != "test-room" { return Outcome::NotSent("destination"); }
    if request.text.trim().is_empty() || request.text.encode_utf16().count() > 4096 {
        return Outcome::NotSent("text");
    }
    if matches!(mode, Mode::Preview) { return Outcome::Preview; }
    sender.send(request) // Exactly one attempt; Unknown is not retried.
}
struct FakeSender { calls: usize, next: Outcome, last_text: String }
impl Sender for FakeSender {
    fn send(&mut self, request: &Request<'_>) -> Outcome {
        self.calls += 1;
        self.last_text = request.text.to_owned();
        std::mem::replace(&mut self.next, Outcome::Unknown)
    }
}
#[cfg(test)]
mod tests {
    use super::*;
    fn fake(next: Outcome) -> FakeSender { FakeSender { calls: 0, next, last_text: String::new() } }
    fn request(text: &str) -> Request<'_> { Request { destination: "test-room", text } }
    #[test] fn disabled_never_dispatches() {
        let mut f = fake(Outcome::Sent(42));
        assert_eq!(execute(&request("hello"), false, Mode::Dispatch, &mut f), Outcome::NotSent("disabled"));
        assert_eq!(f.calls, 0);
    }
    #[test] fn blank_never_dispatches() {
        let mut f = fake(Outcome::Sent(42));
        assert_eq!(execute(&request(" \n"), true, Mode::Dispatch, &mut f), Outcome::NotSent("text"));
        assert_eq!(f.calls, 0);
    }
    #[test] fn other_destination_never_dispatches() {
        let mut f = fake(Outcome::Sent(42));
        let r = Request { destination: "other-room", text: "hello" };
        assert_eq!(execute(&r, true, Mode::Dispatch, &mut f), Outcome::NotSent("destination"));
        assert_eq!(f.calls, 0);
    }
    #[test] fn preview_never_dispatches() {
        let mut f = fake(Outcome::Sent(42));
        assert_eq!(execute(&request("hello"), true, Mode::Preview, &mut f), Outcome::Preview);
        assert_eq!(f.calls, 0);
    }
    #[test] fn success_preserves_text_and_receipt() {
        let mut f = fake(Outcome::Sent(42));
        assert_eq!(execute(&request(" hello \n"), true, Mode::Dispatch, &mut f), Outcome::Sent(42));
        assert_eq!(f.calls, 1); assert_eq!(f.last_text, " hello \n");
    }
    #[test] fn ambiguous_result_is_not_retried() {
        let mut f = fake(Outcome::Unknown);
        assert_eq!(execute(&request("hello"), true, Mode::Dispatch, &mut f), Outcome::Unknown);
        assert_eq!(f.calls, 1);
    }
    #[test] fn utf16_limit_is_inclusive() {
        let mut f = fake(Outcome::Sent(42));
        assert_eq!(execute(&request(&"😀".repeat(2048)), true, Mode::Preview, &mut f), Outcome::Preview);
        assert_eq!(execute(&request(&"😀".repeat(2049)), true, Mode::Dispatch, &mut f), Outcome::NotSent("text"));
        assert_eq!(f.calls, 0);
    }
    #[test] fn definite_refusal_stays_not_sent() {
        let mut f = fake(Outcome::NotSent("refused"));
        assert_eq!(execute(&request("hello"), true, Mode::Dispatch, &mut f), Outcome::NotSent("refused"));
        assert_eq!(f.calls, 1);
    }
}

05 / CONNECT THE MODEL TO REAL CODE · 20 MIN

Now the production code has landmarks.

Read these public source snapshots in order. They are pinned to the revision inspected on 15 November 2026, so future changes will not silently rewrite this lesson.

  1. SendText::validate checks options, blankness and UTF-16 length.
  2. send_message_data checks sending policy, creates a shared deadline, converts inputs, charges the limiter, calls the client, and checks the receipt.
  3. TelegramClientTrait::send_message is the injectable boundary. Its default rejects sending, preserving read-only implementers.
  4. The sending guide documents opt-in writes and exact recipient forms. Read the first paragraph and delivery-outcome section; do not enable sending.

Do not confuse the lab with production: the connector sends immediately when enabled. It does not provide the lab's preview or per-call confirmation dialog. Real recipient forms, authorization, deadlines and receipts are richer. Application-level approval must be handled deliberately.

06 / RECAP · 10 MIN

Explain it before extending it.

  1. Why can a timeout after dispatch not be labeled NotSent?
  2. Why must invalid input produce zero sender calls?
  3. Does one call inside execute guarantee no duplicate across two calls to execute?
  4. Which part of this lab is deliberately stricter or simpler than the real connector?

The remote side may already have acted. Rejected input must never cross the boundary. Two calls are two operations; the lab has no cross-call idempotency. Its fake allowlist, preview and synchronous sender are learning devices, not a full production implementation.
