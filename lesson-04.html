Build a small support router that can pick a reviewed answer or ask for a human, without ever sending a message.

01 · Orientation · 10 min

Move from media to support

Lesson 2 separated a send attempt from its result. Lesson 3 separated media preparation from upload. Today, separate understanding a request from taking action. A FAQ draft can be ready while sending remains entirely out of scope.

Your outcome: a pure Rust function that returns a template ID or a reason for human review, plus an explanation of what this toy should refuse to handle.

Prerequisites: Lesson 3 and basic Rust enums and tests. The simulator works without Rust. To practice the code, use an installed Rust compiler and a disposable scratch folder. No project edits, dependencies, bot setup or real customer messages.

02 · Theory · 25 min

Recognize → decide → draft

Classify: recognize one of four explicit commands. No keyword guessing or model.
Decide: missing, unsupported or extra input goes to human review. This is an explicit output, not a crash.
Draft: a recognized command selects a fixed template ID. Copy is controlled by the app, not interpolated from the request.
Send: absent. Real sending would require a separate adapter and delivery policy. HumanReview does not notify anybody here.

A live Telegram bot receives platform updates using a bot identity, separate from the Rust connector acting through an authenticated Telegram account. The router below accepts only a string; it is not a Telegram update parser. The commands are fictional lab commands, not a claim about the live TeleShelf bot.

InputOutput
/install or /updateDraft the corresponding help template.
/watchlater or /favoritesDraft the corresponding saved-video explanation.
Empty / ASCII whitespace onlyHumanReview(Empty)
Recognized first token plus extra wordsHumanReview(Ambiguous)
Anything else, including /install@botHumanReview(Unknown)

Compare the first token case-insensitively for ASCII. Leading and trailing ASCII whitespace is ignored. Check whether the first token is recognized before checking for extra tokens, so /help /install stays Unknown. The narrow grammar is a teaching choice, not production support for groups, languages or Telegram command entities.

Read Telegram’s command guide (the Commands section), then Rust’s enum matching chapter (through exhaustive matching).

03 · Predict, then run · 15 min

Try a support request

Use only invented input. Predict the result before pressing Run. The simulator does not store, repeat or transmit your input.

Predict: draft or human review?
Four experiments and what they show
  1. Put spaces around /INSTALL. ASCII case and whitespace do not change the command.
  2. Try /install /update. One recognized command plus extra input is Ambiguous.
  3. Try how do I update?. A word inside free text is not an explicit command.
  4. Try /favorites send this now. The extra words never select an action or become part of a draft.

Templates are teaching copy, not production bot replies. Review the current installation guide, update notes and feature documentation before reusing any wording.

04 · Code and tests · 40 min

Implement only the routing policy

Download the starter to a scratch folder. It has the result types and tests, with route left for you. First compile and run the tests. They should fail at todo!. Then implement the rule table without adding a sender, file access or any dependency.

rustc --edition=2021 --test lesson-04-starter.rs -o lesson04-tests
./lesson04-tests
  1. Split the input into ASCII-whitespace-separated tokens. If there is no first token, return Empty.
  2. Map just the first token to a template, comparing the complete token. Return Unknown if it has no match.
  3. If a recognized token has a second token, return Ambiguous. Otherwise return Draft with the template ID.
  4. Run all tests again. Add a case of your own that catches a tempting shortcut, such as starts_with("/install").
Hint: keep the data flow narrow

split_ascii_whitespace() skips outer whitespace without a separate trim. Consider eq_ignore_ascii_case or an ASCII-only lowercase copy for matching. The returned enum never needs to retain the input string.

Reference implementation and tests

Read Writing Tests in Rust if you want a refresher on assertions. The tests check routing behavior on chosen fixtures, not customer satisfaction, permission checks or a real bot.

05 · Exit check · 15 min

Explain where the rule stops

  1. Why is Draft(Favorites) neither permission nor proof of sending?
  2. What user question would this router hand off even though a human could understand it?
  3. Which test would catch an accidental change that routes /install@bot as /install?
  4. In a real support system, what would have to happen between HumanReview and a human actually seeing the request?
Compare your answers

A draft is local data. Natural-language requests are outside the grammar. A dedicated bot-suffix test catches the broadened match. A real handoff requires a separately designed, authorized queue or notification with privacy and delivery rules.

Optional 20 minutes: Write six fictional support requests that a real user might send. Label the right decision before running them. Count correct draft, wrong draft and human review separately. Name one case where a handoff is desirable and one where it adds avoidable work. Don’t loosen rules just to increase draft count.
